# Siming 1.0 stable contract

This is the normative supported profile for the five-package Siming family. It supersedes preview-only compatibility statements. Release status and evidence live in the qualification ledger; this document alone does not claim publication.

## Stable surface

Every entry in each `PublicAPI.Shipped.txt` is intentional. Core contracts/records/errors, raw and typed payload serialization, both named canonical serializers, format v1/v2/v3 helpers, checkpoint and verification APIs, the ephemeral in-memory reference provider, SQLite options/provider/errors, detached signing/verifying, provider conformance and verifier Program.Main/RunAsync remain supported. No constructor is extended or removed for graduation. Internal fault hooks, sample code and implementation helpers are not public promises.

The format helper APIs deliberately allow independent encoders and verifiers. A DTO is data, not proof of a valid committed entry. Validation occurs at the operation boundary. Positional record constructors/init/with/deconstruction retain their existing signatures; do not extend those constructors in 1.x. New optional capabilities must be separate interfaces or compatible overloads/body properties, not new required members of an existing provider interface.

## Ownership and lifetime

- Raw append inputs are validated and copied before the first asynchronous suspension in the built-in providers. Typed payloads are synchronously serialized by the supplied serializer before that copy. The caller must not mutate a typed object while it is being serialized. Serializer failures propagate before any storage change.
- Requests and manually constructed DTO records are shallow values: a ReadOnlyMemory field is not a deep-immutability promise about caller-supplied backing storage. Callers own those buffers. Provider-returned entries are detached from retained provider state; modifying an accessible result buffer cannot rewrite history. Reusing returned entries as application state is the caller's responsibility.
- LedgerHash copies construction bytes and returns detached copies; equality compares all 32 bytes, including the zero-valued default. Hash-code numeric values are not serialized identifiers. HMAC keys own a copy, expose detached secret copies, and never persist secrets. Clear/Dispose is idempotent and terminal; subsequent cryptographic use throws ObjectDisposedException. Reading Secret after clear returns zeros. The caller owns the key and must keep it live, unchanged and undisposed until all borrowing operations/providers complete; disposal concurrent with use is unsupported.
- Providers borrow serializer, TimeProvider and key dependencies; they do not dispose those caller-owned services. Dispose providers only after pending calls/enumerations have settled. The SQLite provider owns its connections; disposing clears its matching pool for archival. InMemory owns ephemeral state and has no restart durability.
- Record equality is CLR record field equality: ReadOnlyMemory and IReadOnlyList fields do not imply structural byte/sequence equality. Do not use generic DTO Equals/GetHashCode for semantic event identity. Retry equivalence is the independently defined exact payload/descriptor comparison; hash/checkpoint/head/context values have their explicit value semantics. Returned object identity and reuse of the same instance are unspecified.

## Ordering, append and retry

One ledger epoch has one immutable LedgerId and gap-free global sequence starting at 1. An empty head is sequence 0 with that epoch's genesis. Stream IDs are exact ordinal logical partitions, not independent chains. No normalization of application identifiers is promised; existing format UTF-8 encoding is defined by the fixed formats/vectors.

Append atomically reads the head, evaluates the request, assigns the next sequence, hashes the exact copied bytes, inserts and commits. No sequence is consumed by rejected/rolled-back work. Successful equivalent retries under the same ledger-wide idempotency key return the original entry, even when ExpectedHead is stale. Different content under that key throws LedgerIdempotencyConflictException. For a new key/no key, mismatched ExpectedHead throws LedgerHeadConflictException with both heads. Equivalence includes stream, event type, media/serialization descriptors/version and exact payload bytes, excluding generated sequence/time/hash and expected-head precondition.

Independent SQLite instances/processes serialize writers transactionally. There is no transaction spanning ledgers or applications, no exactly-once guarantee for external effects and no distributed coordination. Cancellation is cooperative; an interrupted or lost response does not prove that nothing committed. Reconcile via the same idempotency key. Without a key, callers cannot obtain automatic retry deduplication. Diagnostic prose and exact race timing are unspecified; public error categories/properties and mutation outcomes are the contract.

## Reads and verification

Paged reads have an exclusive global AfterSequence and positive Limit ≤ 10,000; ascending sequence and exact optional stream filter. Each query is independent. Append-only history means new rows between pages cannot rewrite earlier rows; continuing the last observed sequence avoids duplicates. Later appends can appear in later pages; pages are not a single transaction/snapshot. The unpaged async enumeration remains streaming/cancellable, not an in-memory unlimited-materialization requirement on providers. Never assume a stream-only read is independently verifiable.

VerifyAsync captures a target head and verifies its complete prefix using bounded pages; later appends do not invalidate the captured prefix. SQLite does so on one read transaction/connection. Verification compares exact fields and optional independently retained checkpoint; malformed/unsupported data produces the defined failure category or schema/import error. Provider I/O exceptions and custom progress callback exceptions propagate; cancellation propagates as OperationCanceledException. Verification proves consistency relative to the trusted head/checkpoint, not truth, identity, permission, secrecy or accurate wall-clock time.

## Bounds and formats

LedgerInputLimits defaults are stable: payload 16 MiB; stream/idempotency key 1,024 UTF-8 bytes; event type 512; content/serializer format 256. Hosts can select positive custom limits. Oversized append inputs fail before mutation with LedgerInputLimitExceededException and field/observed/maximum sizes. Time is UTC Unix milliseconds; no strict wall-clock monotonicity promise. Context/key IDs and canonical number/exponent/output bounds remain those in the shipped constants and vectors.

Ledger epochs 1/2/3 and canonical JSON versions 1/2 remain independently named contracts. V1 canonicalization is historical, including its number conversion behavior; v2 preserves token-level numbers and rejects duplicate properties. No package upgrade rehashes or reinterprets old bytes. CLR object serialization options/types are application-owned; the stable canonical guarantee starts at the resulting JsonElement/bytes. Supported byte and source-generated JsonTypeInfo paths retain their documented trimming behavior; generic reflection APIs retain annotations. Native AOT linking is NOT PROVEN by analysis alone.

Portable checkpoint document v1 and signed envelope v1 exports preserve field order and exact byte encoding. Imports are bounded (64 KiB checkpoint, 256 KiB signed envelope, depth 16), reject missing/wrong-typed required fields and duplicate top-level names. Optional unknown properties are ignored under v1; adding mandatory properties requires a new document version. GUIDs/hash text may be accepted in the existing parser's representation and canonical re-export does not preserve arbitrary input spelling/property order/unknown fields. Unknown document versions fail FormatException; unknown/incompatible ledger epochs fail NotSupportedException or provider compatibility error. Importing a signed envelope does not authenticate it.

## Signing, verification tool and conformance

Signing is synchronous; the caller owns/disposes signers. Built-in Ed25519 signing keys are non-exportable unless explicitly opted in, imported private keys are non-exportable, and public keys are exportable. External signer/verifier exceptions propagate; Sign/Verify do not conceal provider failure as a successful signature. Signature mismatch returns false. A signature authenticates the document, not its asserted history; still verify the ledger against the checkpoint. Capturing epoch-3 heads requires the caller to attach the exact suite/key binding before export; CaptureAsync cannot infer caller-owned keys from a generic ledger.

The verifier is supported as a dotnet tool and through Program.RunAsync with argument strings, caller-owned TextWriters and cancellation. It does not dispose supplied writers. It opens existing databases read-only, returns 0 success, 1 invalid history/signature, 2 handled input/compatibility error, 130 requested cancellation. JSON result/error field names and category meanings are stable; unknown optional output fields must be ignored by consumers. Exact error prose/help/progress timing is unspecified. Null writers/argument collections are programmer errors; no guarantee converts every arbitrary infrastructure exception to an exit code. Program.Main owns only its console cancellation subscription. Prefer ledger/verifier APIs when CLI parsing is unnecessary.

Testing.RunAsync is a provider-neutral epoch-1 conformance check over a factory-supplied empty provider. It catches test failures into its result; factory/provider disposal belongs to the caller. It does not certify every epoch, restart, I/O, platform or protection policy. Returned check-list instances from the suite are read-only snapshots; manually constructed results retain ordinary shallow record semantics.

## SQLite schema, recovery and migration

The current schema/columns/constraints/triggers and ledger format marker are retained. Existing qualified preview.7 databases can be opened with 1.0 without rewrite or migration. Read-only open validates existing schema without creating/migrating it. Incompatible schema, altered required objects or mismatched epoch/context fail closed with SimingSchemaCompatibilityException. Unknown OpenMode and invalid BusyTimeout are rejected before storage access.

1.x readers retain support for existing supported epochs and canonical contracts. Writers keep the opened epoch/format and may not silently upgrade it. A future incompatible schema/format needs an explicit new version, reviewed opt-in migration/export strategy, backup guidance and compatibility evidence. Downgrade to preview is SUPPORTED BY THE unchanged-format probe for ordinary supported data, not a blanket promise about future packages. Restore backups instead of lowering markers. Back up database/WAL consistently, retain checkpoints independently and keys separately; application payload retention and authorization policy remain outside Siming.

## Compatibility and exclusions

For 1.x, source signatures, binary signatures (AssemblyVersion 1.0.0.0), documented defaults, supported observable behavior and existing persisted/wire contracts are preserved. Minor releases add compatible APIs; patch releases fix defects without revising those contracts. Renames/removals/constructor growth/required provider methods, changed meanings/defaults or reinterpretation require a major API/new format decision. Exceptions for invalid/unsupported input remain fail-closed; exact exception prose is not stable. Assemblies/packages stay immutable once published; shipped baselines and selected SDK package baseline enforce review.

Preview.7→RC preserves public signatures but intentionally fixes mutable aliases, cleared-key reuse, invalid SQLite options and duplicate checkpoint JSON handling. Recompile is not required for the qualified unchanged preview consumers, but new behavior is recorded in release notes. RC→1.0 must pass the same unchanged-binary and persisted-data probes. Consumer probes state their scope, not universal application compatibility.

OUT OF SCOPE: Merkle proofs, replication/network/consensus, remote/HSM signers, new formats/suites, independent per-stream chains, retention/redaction policy, new frameworks, performance rewrites, Hufu and Gagamba. No experimental public placeholders were found or added.
